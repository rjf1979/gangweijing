# 岗位镜多流程产品与开发文档

版本：V0.1  
日期：2026-08-06  
适用范围：求职者端 Web 工具

## 1. 设计原则

岗位镜不是一条固定的四步向导，而是围绕“账号、简历资产、岗位分析任务、报告、邮件”形成多条可独立进入和恢复的流程。

- 简历属于账号资产，上传一次后可复用，不随单份报告重复上传。
- 每次岗位分析都是独立任务，可使用同一份已确认简历。
- 报告生成与邮件发送是两个状态；邮件失败不影响在线查看。
- 页面根据账号数据判断入口，不能只依赖浏览器临时状态。
- 用户主动更新简历时才进入重新上传流程。

## 2. 独立状态维度

### 2.1 账号状态

`guest -> authenticated -> session_expired`

### 2.2 简历状态

`missing -> uploaded -> parsed -> needs_confirmation -> confirmed -> updating`

当前 V0.1 已保存简历文本；后续需单独保存 `resumeStatus` 和确认时间。

### 2.3 岗位任务状态

`draft -> recognizing -> needs_confirmation -> queued -> analyzing -> completed | failed`

当前 V0.1 的分析是同步请求，`queued` 和可恢复的 `analyzing` 为后续任务队列能力。

### 2.4 报告状态

`not_created -> generating -> available -> archived`

### 2.5 邮件状态

`not_requested -> pending -> sent | failed`

邮件状态不得覆盖报告状态。

## 3. 流程 A：首次注册并建立简历档案

**起点**：未登录且账号不存在。  
**路径**：`/ -> /resume -> /facts`  
**结束条件**：账号已创建，简历已保存并完成事实确认。

1. 用户输入邮箱和密码注册。
2. 系统自动登录并检查账号简历。
3. 简历不存在，进入 `/resume`。
4. 用户上传 PDF/DOCX 或粘贴文本。
5. 系统提取文本并保存到当前账号。
6. 进入 `/facts`，用户修正并确认职业事实。
7. 系统保存确认后的版本，并进入岗位分析入口。

异常分支：邮箱已注册时切换到登录；解析失败时保留当前页并允许重新上传；保存失败时不得进入下一页。

## 4. 流程 B：已有简历用户登录

**起点**：账号已有简历。  
**路径**：`/ -> /facts`  
**结束条件**：用户开始分析岗位或进入报告列表。

1. 用户登录，或系统恢复 30 天会话。
2. 前端请求账号简历状态。
3. 已有简历时跳过 `/resume`。
4. 默认进入 `/facts`，显示最近确认的简历内容。
5. 用户可以继续分析岗位，也可以进入 `/reports`。

禁止行为：不能因为刷新、换路由或浏览器临时草稿丢失而再次要求上传。

## 5. 流程 C：主动更新简历

**起点**：已登录且已有简历。  
**建议入口**：账号菜单中的“更新简历”。  
**路径**：`/resume?mode=replace -> /facts`  
**结束条件**：新版简历确认并替换账号当前版本。

1. 用户主动点击“更新简历”。
2. 页面明确提示更新只影响之后生成的报告，不修改历史报告。
3. 用户上传或粘贴新版简历。
4. 系统解析后进入事实确认。
5. 用户确认后替换当前简历，并记录更新时间。

后续建议：保存简历版本号，使报告记录使用的 `resumeVersionId`。

## 6. 流程 D：通过岗位截图创建分析

**起点**：已登录且简历已确认。  
**路径**：`/job -> /report -> /report/:token`  
**结束条件**：在线报告可访问。

1. 用户上传岗位截图。
2. AI 识别公司简称、岗位名称和完整 JD。
3. 页面显示识别结果，用户负责最终确认。
4. 用户提交后创建独立岗位分析任务。
5. AI 依据已确认简历和 JD 生成证据型报告。
6. 系统保存报告并生成随机访问令牌。
7. 页面进入在线报告，并显示永久报告地址。

识别不确定时必须返回 warnings；公司或岗位无法识别时允许用户手动补充，不得臆造。

## 7. 流程 E：通过文本 JD 创建分析

**起点**：已登录且简历已确认。  
**路径**：`/job -> /report -> /report/:token`  
**结束条件**：在线报告可访问。

1. 用户粘贴 JD 文本。
2. 用户填写或确认公司简称和岗位名称。
3. 未填写时，分析模型从 JD 中提取；无法确认则使用“未知公司”或“未命名岗位”。
4. 后续生成、保存和查看逻辑与流程 D 相同。

## 8. 流程 F：报告生成失败与恢复

**起点**：岗位材料已确认。  
**结束条件**：生成成功，或用户明确取消。

1. 创建任务后立即保存输入快照和任务状态。
2. AI 请求失败时将任务标记为 `failed`，保留失败原因和重试次数。
3. 页面显示“重新分析”，不得要求用户重新上传简历和岗位。
4. 重试复用原任务输入，成功后生成报告令牌。

当前缺口：V0.1 使用同步请求，刷新期间不能恢复分析进度；下一版本应引入持久化任务和轮询接口。

## 9. 流程 G：在线查看与管理报告

**入口一**：生成完成后进入 `/report/:token`。  
**入口二**：从 `/reports` 打开历史报告。  
**结束条件**：用户完成查看、复制链接或开始新岗位分析。

报告名称统一为：

`YYYY-MM-DD_公司简称_岗位名`

示例：`2026-08-06_字节跳动_产品经理`

规则：使用报告创建日期；去除公司工商后缀；过滤文件名非法字符；缺失字段使用明确占位词。报告列表与在线报告标题必须使用同一个持久化名称。

共享链接持有者可查看报告，因此页面必须提示不要公开分享；接口响应设置 `private, no-store`。

## 10. 流程 H：邮件发送与失败重试

**起点**：报告已经保存并获得在线地址。  
**结束条件**：邮件发送成功，或保持失败状态等待重试。

1. 报告完成后先返回在线地址，不等待邮件决定报告是否成功。
2. 邮件只发送报告摘要和在线地址，不发送完整简历。
3. 成功写入 `emailStatus=sent`。
4. 失败写入 `emailStatus=failed`，报告仍为 `completed`。
5. 报告列表提供“重新发送邮件”，不得重新运行 AI 分析。

验证邮件和报告邮件统一使用环境地址配置。`APP_URL_MODE=local` 时读取 `LOCAL_APP_URL`，`APP_URL_MODE=server` 时读取 `SERVER_APP_URL`。正式上线时将 `SERVER_APP_URL` 配置为公开 HTTPS 域名，并使用 Resend 已验证的 ASCII 发件地址。

## 11. 流程 I：会话过期恢复

**起点**：用户操作期间会话失效。  
**结束条件**：重新登录后回到原任务。

1. API 返回 401 时保存非敏感页面草稿和当前路由。
2. 显示登录页，不清空岗位内容。
3. 登录成功后重新检查账号简历，并恢复到原流程。
4. 共享报告页不依赖登录；个人报告列表必须登录。

## 12. 页面入口判定

| 当前状态 | 默认入口 |
|---|---|
| 未登录 | 登录/注册页 |
| 已登录、无简历 | `/resume` |
| 已登录、有简历、无当前岗位任务 | `/facts` 或 `/job` |
| 岗位待确认 | `/job` |
| 报告生成中 | 分析进度页 |
| 报告已完成 | `/report/:token` |
| 查看历史记录 | `/reports` |

访问 `/resume` 时，已有简历用户默认跳转 `/facts`；只有显式进入更新模式才显示重新上传页面。

## 13. 数据模型最低要求

- `User`：账号、当前简历、简历状态、简历更新时间。
- `ResumeVersion`：原始文件信息、解析文本、确认文本、版本时间（下一版本）。
- `AnalysisTask`：用户、简历快照、岗位快照、任务状态、失败原因、重试次数。
- `Report`：任务、报告名称、随机令牌、结构化结果、创建时间。
- `EmailDelivery`：报告、收件邮箱、发送状态、服务商消息 ID、失败原因。

## 14. V0.1 验收标准

- 已上传简历的账号再次登录不会看到上传引导。
- 岗位页不会混入简历事实文本。
- 截图和文本两种岗位入口都可独立生成报告。
- 报告标题和列表名称均符合日期、公司简称、岗位名规则。
- 在线报告可通过随机链接重新打开。
- 邮件失败不影响报告状态和在线查看。
- 每条失败流程都有明确重试入口，不要求重复提交无关材料。

## 15. 推荐开发顺序

1. 完成账号级简历状态与更新简历入口。
2. 将岗位分析改为持久化任务，支持刷新恢复和失败重试。
3. 补齐报告统一命名和旧报告兼容展示。
4. 增加邮件重发接口及服务商消息 ID。
5. 增加简历版本和报告输入快照，保证历史报告可核实。
